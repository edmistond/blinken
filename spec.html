Summary

Blinken is a local-first command-line tool that lets coding agents record the consequential places where they had to guess, because the spec, docs, tests, or existing code did not clearly determine an answer.

It is not a transcript. A long autonomous run produces tens of thousands of lines of activity but only a few dozen decisions that materially determine whether the result is right. Blinken captures those decisions when they happen, ranks them for human review, and makes it comfortable to accept them, reject them, or mark them for follow-up. Think of it as observability for agent judgment.

The user-facing noun is guess. Internally the code may use neutral names such as GuessRecord where that reads better.

Agent hits a consequential ambiguityduring the run
Agent records one cheap guessone short command
Human sees the important guesses firstterminal or browser
Human accepts, rejects, or follows upstate persists

The one loop v0.1 must make excellent. Everything else is optional until it proves useful.

Problem statement

Code review becomes less sufficient as agents work for longer stretches. An implementation can be locally coherent and mechanically correct while resting on an early, consequential interpretation the user never intended.

Agents are also poor witnesses to their own earlier reasoning. Asking for a reconstructed ledger at the end of a run yields an incomplete or overly tidy account. Recording a guess therefore has to be cheap enough to do at the moment the ambiguity is met.

A record is worth keeping when all three hold:

  • The agent had to choose among materially different behaviors or approaches.
  • The available spec, docs, tests, code, or conventions did not clearly determine the answer.
  • The choice could matter to the user, product, system, data, security, maintainability, or externally visible behavior.

Routine implementation details do not belong in Blinken.

Goals and non-goals

Blinken should

  • Record consequential guesses with very little invocation and output overhead.
  • Work without a hosted service, account, API key, or network.
  • Store records durably in a user-level SQLite database shared by local agent sessions.
  • Detect the current project and capture the working directory at record time.
  • Associate guesses with logical agent sessions when possible.
  • Rank unresolved guesses by review value: confidence, impact, reversibility.
  • Offer a compact CLI workflow and a comfortable local browser workflow.
  • Let a human accept, reject, or flag guesses, with optional notes.
  • Preserve enough context to understand a guess without becoming a transcript.
  • Play well with RTK and other token-saving wrappers via small, deterministic output.
  • Leave room for optional local semantic similarity with no LLM calls.
  • Stay useful at MVP scale with no embeddings, clustering, daemon, or cloud.

Blinken is not

  • An agent orchestrator.
  • A transcript, tool-call, or command-output recorder.
  • A logging or telemetry platform.
  • A source-code review system or task tracker.
  • A replacement for docs, tests, specs, or ADRs.
  • Something that edits source code after a rejection.
  • A cloud sync service.
  • An LLM-based summarizer or classifier.
  • A vector database.
  • An editor plugin, MCP server, hosted dashboard, or always-on daemon.

Any of these may be explored later only if real usage demonstrates a need.

Design principles

Local first

Recording, storage, querying, ranking, and review all work offline. No record leaves the machine in normal operation.

Cheap at the moment of uncertainty

The write path is a single short command. Optional metadata improves a record but never makes recording burdensome.

Human judgment stays authoritative

Scores and similarity matches are review aids. Blinken never silently decides two guesses are the same, nor treats a model's confidence as calibrated truth.

Agent output and human output differ

Agent-facing commands default to compact, deterministic text. Human review may be verbose and prefers legibility over token economy.

Boring, replaceable internals

Ordinary Go and SQLite patterns. Abstraction only around what is likely to change, chiefly local embedding generation. No ceremonial clean architecture.

Primary workflows

Start a session. Optional. The returned identifier can be exported so later commands pick it up. An explicit --session wins over the environment variable. No process-tree heuristics.

blinken session start --agent codex --model gpt-5.6
01K...
export BLINKEN_SESSION=01K...

Record a guess. The positional argument is the summary. Project root, cwd, time, and session are inferred. Source files are never inspected.

blinken guess "Suspended users retain read-only access"
01K...

# rich form
blinken guess \
  --kind inference --confidence medium --impact high --reversibility hard \
  --summary "Suspended users may download existing files" \
  --ambiguity "The spec defines write restrictions but not read access" \
  --reason "Neighboring handlers treat suspension as write-disabled" \
  --alternative "Block all file access" \
  --would-ask "Should suspension make existing files inaccessible?" \
  --file src/Files/DownloadHandler.cs:118

Inspect compactly. The default is one summary line. Compact rows expose individual records with documented, stable abbreviations. JSON is available but usually costs more tokens.

blinken guesses
8 unreviewed | 2 high-impact | 3 low-confidence

blinken guesses --compact
01K... H/L assumption Suspended accounts retain downloads
01K... M/M inference  Failed payments retry once

Review. Defaults to the current project, unreviewed and followup guesses, highest priority first, with the ordering factors shown rather than an opaque score. The browser variant serves an ephemeral loopback server on a random port and opens the browser unless told not to. No daemon.

blinken review
blinken review --serve --no-open
http://127.0.0.1:43817

Resolve. These commands update review state only. Bulk actions report the count and require confirmation unless --yes is given.

blinken accept 01K...
blinken reject 01K... --note "Suspended accounts must have no file access."
blinken followup 01K... --note "Confirm with product before release."
blinken accept --all --status unreviewed --impact low

CLI surface

The proposed v0.1 command set. guess is the preferred verb; a record alias may exist for discoverability. No separate infer, tradeoff, or deviate commands, since --kind is sufficient.

blinken guess [text] [options]
blinken guesses [filters] [--compact|--json]
blinken show <guess-id> [--json]
blinken review [filters] [--serve] [--no-open]
blinken accept|reject|followup <guess-id> [--note text]
blinken accept|reject|followup --all [filters] [--note text] [--yes]
blinken session start [--agent name] [--model name] [--label key=value]
blinken session end [session-id]
blinken sessions [--compact|--json]

Cross-command conventions

  • Successful writes print only the affected identifier. --quiet prints nothing.
  • --json follows a documented schema and writes JSON only to stdout. Diagnostics go to stderr.
  • Exit code 0 is success. Nonzero codes distinguish usage, missing record, storage, and unexpected failures.
  • Color and glyphs are never required to read output. Respect NO_COLOR and disable decoration when redirected.
  • No progress animation for fast operations.
  • RTK compatibility comes from economical normal behavior, not a Blinken-specific plugin.

Review priority

Confidence alone is not an adequate ordering. A low-confidence naming choice may be harmless, while a fairly confident decision about deletion, security, money, or an external contract deserves immediate attention.

review priority = uncertainty × impact × difficulty of reversal

v0.1 uses a small deterministic heuristic with a plain product. Ties break deterministically, by impact and then creation time. The number is a sorting aid, not a measurement: review output leads with the three labels and a plain-language reason, and the raw score lives in JSON rather than dominating the human UI. The ranking rules live in one testable component shared by the CLI and browser.

8
2 × 2 × 2
medium impact, moderate to reverse

Weights: uncertainty low 3 / medium 2 / high 1. Impact low 1 / medium 2 / high 3 / critical 5. Reversibility easy 1 / moderate 2 / hard 3. Range 1 to 45.

Projects and sessions

Project detection

Data lives in a user-level database, never inside the repository. Starting at the working directory, detection walks upward looking for, in order:

  1. An explicit project root supplied by the caller.
  2. An optional Blinken project marker or config file.
  3. A Jujutsu or Git repository boundary. Worktrees must work, so .git is not assumed to be a directory.
  4. A reasonable fallback root for a non-repository project.

Identity uses the least invasive strategy: a stable opaque project id in the user database, aliases from observed canonical roots, and a separate display name. No required .blinken file, and no identity derived solely from a remote URL. Moving a repository may create a new alias or need an explicit link command; perfect move detection is not an MVP requirement.

Cwd is captured separately from the project root, as both the canonical absolute path and a computed project-relative path. Users can disable or redact path capture.

Sessions

A session records an id, optional project, start and optional end timestamps, optional agent and model names, initial working directory, and bounded key/value labels. Concurrent sessions write to the same database. Session end is advisory; abandoned open sessions are valid and never block review.

Storage

SQLite through Go's database/sql with a small, well-supported driver. Whether the driver needs CGO must be documented before committing to it, and the build matrix proven early.

macOS    ~/Library/Application Support/blinken/blinken.db
Linux    $XDG_DATA_HOME/blinken/blinken.db  or  ~/.local/share/blinken/blinken.db
Windows  %LOCALAPPDATA%\blinken\blinken.db
override BLINKEN_DB=... or --db <path>

Requirements

  • Write-ahead logging enabled.
  • Bounded busy timeout; short write transactions.
  • Automatic, ordered, versioned migrations.
  • Recoverable migration failure before any destructive migration exists.
  • Foreign keys on.
  • Raw SQL and schema are not the public automation contract.
  • Inspection with ordinary SQLite tools documented as an escape hatch.

Initial tables

  • projects
  • project_paths
  • sessions
  • guesses
  • guess_files

Similarity tables (subjects, embeddings, dismissed pairs) wait until that capability is built, unless a nullable subject id materially simplifies the first migration.

Browser review

blinken review --serve runs inside the same Go executable on the standard net/http server. The UI is plain HTML, CSS, and small vanilla JavaScript modules, compiled into the binary with embed.FS and served from the same origin as its JSON or form endpoints. Crit is the architectural prior art for this packaging shape, without its broader review, proxy, or daemon features.

The initial UI provides

  • Current project and optional session selection.
  • Counts for unreviewed, high-impact, and low-confidence guesses.
  • A priority-sorted review queue with filters for status, kind, confidence, impact, and session.
  • Full guess detail: ambiguity, choice, reason, alternative, would-have-asked.
  • Project-relative cwd and file references.
  • Accept, reject, follow-up, with optional note, individually or in bulk.
  • Clear movement to the next unresolved guess after an action.
j / knext / previous aaccept rreject ffollow-up enterexpand or focus

Shortcuts are desirable, not a release blocker.

Local web security

The server has write access to the database and is treated accordingly.

  • Bind only to 127.0.0.1 and ::1. No external-listen option without deliberate auth design.
  • Random available port by default; the terminal prints the exact bound URL.
  • Reject non-loopback Host headers to blunt DNS rebinding.
  • Anti-CSRF protection on every state-changing request.
  • No permissive CORS. No user content rendered as raw HTML.
  • Server stops when the foreground process exits.

Privacy, redaction, and deletion

The database may hold proprietary decisions, paths, URLs, or secrets pasted into free text, and is documented as sensitive local data. Blinken must never capture environment variables, command output, or source-file contents automatically. It records only explicitly supplied text plus the small set of inferred metadata described above, and applies configured redaction before persistence, not just at display time. There is no telemetry.

blinken delete <guess-id>                      # soft delete
blinken delete --project . --before 2026-01-01
blinken purge --hard --deleted-before 2026-01-01  # permanent, explicit
  • Delete is soft in v0.1. No restore UI yet, but the row must remain structurally recoverable.
  • Hard purge is the deliberate privacy escape hatch for already soft-deleted records. Whether SQLite reclaims space immediately is documented honestly.
  • Filtered deletion and purge show the match count and require confirmation unless --yes is passed.
  • Redaction may use literal values, user regexes, or glob-like path rules. Built-in heuristics may catch common credential shapes but are never claimed to be complete.
  • No database encryption in the MVP. Rely on OS disk encryption and filesystem permissions.

Configuration

Optional. Defaults work with no config file, stored in the OS-appropriate user location. A project-local file may come later, but Blinken never writes into a repository merely because it was invoked there. Precedence: command-line options, then environment variables, then user config, then built-in defaults.

[recording]
capture_cwd = true
capture_files = true

[privacy]
redact = ["literal-sensitive-value"]
ignore_paths = [".env", "secrets/**"]

[review]
open_browser = true
include_followup = true

Implementation architecture

One executable containing the CLI, local server, migrations, and browser assets. The cmd/blinken package stays a thin composition root. Packages stay cohesive without inventing interfaces and boundaries to imitate a large service. Six layers for a tiny first release would be theater.

cmd/
  blinken/          # package main and composition root
internal/
  cli/              # command parsing and output contracts
  core/             # models, validation, ranking, use cases
  storage/          # SQLite access and migrations
  server/           # loopback HTTP handlers
web/                # embedded browser assets and embed.go
  • Standard-library net/http with explicit timeouts and graceful shutdown.
  • embed.FS for frontend assets, same process and origin as the review API.
  • Plain HTML, CSS, and vanilla JavaScript until measured UI complexity justifies a toolchain.
  • database/sql with small explicit data-access code and a deliberately chosen SQLite driver.
  • A mainstream CLI parser picked after checking maintenance, help output, testability, and ergonomics. The standard flag package is acceptable if it fits.

Do not distort the domain model, web UI, or migration strategy merely to avoid CGO before the tradeoff has been measured. Compare pure-Go and CGO-backed SQLite empirically on correctness, portability, build complexity, performance, and size.

Deferred packaging

Automated releases, GitHub Actions workflows, checksummed artifacts, and package-manager publication are explicitly not v0.1 objectives. Development uses go run and go build. After the core loop is proven: GitHub Releases as the source of truth, then Homebrew, winget or Scoop, and go install, in whatever order maintainer capacity allows. Neither npm nor Python should be required to install.

Semantic similarity, later

An optional capability after v0.1, never required to record, list, or review. No LLM query, no hosted embedding API, no network. A small local embedding model sits behind a thin boundary because its runtime and packaging are likely to change. If embedding generation fails, recording still succeeds.

type EmbeddingGenerator interface {
    Generate(ctx context.Context, text string) (Embedding, error)
}
  • Input is built from summary, ambiguity, chosen behavior, reason, alternative, and would-have-asked. Never timestamps, model names, absolute paths, or session ids.
  • Storage keeps compact binary vectors with model id, version or checksum, dimensions, encoding, input-format version, and timestamp. Vectors from different model versions are never compared.
  • Matching starts as brute-force cosine similarity within the current project. No vector database or ANN index until measured data demands one. Results are suggestions, shown as a scored list of possibly related guesses.
  • Subjects are created only by explicit human grouping. A not-related action suppresses the same suggestion again where that is simple.
  • Structural locality from cwd and file references is stored now but not folded into a scoring formula until evaluation data supports it.

Testing expectations

Temporary local databases and deterministic fixtures. No test requires network access or credentials.

Unit

  • Guess validation and defaults.
  • Priority ordering and tie-breaking.
  • Project-relative path handling.
  • Compact text formatting and JSON schema.
  • Redaction before persistence.

Storage integration

  • Fresh database creation and ordered migration from every supported version.
  • WAL mode with concurrent short writes; busy-timeout behavior.
  • Foreign-key enforcement, review updates, deletion and purge scoping.
  • Recovery from failed migrations where applicable.

CLI end-to-end

  • Minimal guess prints only an id and creates the expected record.
  • --quiet, redirected output, NO_COLOR, stderr, and exit-code contracts.
  • Project and cwd detection in Git, Jujutsu, and non-repository fixtures.
  • Session env-var versus explicit-option precedence.

Browser

  • Server binds only to loopback.
  • Every asset present in embed.FS with the expected content type.
  • Queue and filters render safely; user text is HTML-escaped.
  • Accept, reject, follow-up, and notes update the database.
  • CSRF protection rejects invalid state-changing requests.

Cross-platform CI and packaged-artifact smoke tests arrive with automated releases. Before similarity suggestions ship on by default, a small labeled set of real guesses measures whether the local model retrieves meaningfully related decisions. The acceptance threshold is a product decision, not a cosine number.

MVP acceptance criteria

Version 0.1 is useful when all of the following hold. Embeddings, similarity, and subjects are not required.

  1. An agent can start a session and record a guess with one short command.
  2. Recording succeeds offline into the user-level SQLite database.
  3. Multiple local sessions can write without ordinary lock failures.
  4. Project, cwd, time, and supplied metadata are persisted accurately.
  5. The default successful write output is only an identifier.
  6. A user can list and review unresolved guesses in deterministic priority order.
  7. A user can accept, reject, or mark a guess for follow-up with an optional note.
  8. The browser review offers the same core actions in a loopback-only UI.
  9. No telemetry, network request, LLM call, or hosted account is required.
  10. Tests cover ranking, storage, the CLI contract, the redaction boundary, and browser write actions.

Phased roadmap

Progress as of 2026-09-10. Phase 0 shipped in commit adff0df: a working Kong CLI, ULID ids, modernc SQLite with WAL proven across processes, and a single binary serving the embedded review UI on loopback. Evidence and recommendations are in docs/phase0-decisions.md; the CLI vocabulary walkthroughs are in docs/example-sessions.md. Phase 1 is underway.

Phase 0

Product spike

  • Validate the CLI vocabulary with hand-written example sessions.
  • Decide the CLI parser and ID format.
  • Prove SQLite WAL behavior with concurrent writers.
  • Prove one Go executable can embed the browser assets and host the loopback UI.
Phase 1

v0.1, a useful ledger

  • User-level database and migrations; project and cwd detection; optional sessions.
  • guess, guesses, show, review-state commands, terminal review.
  • Deterministic priority; compact output and optional JSON.
  • Loopback-only review --serve with a basic embedded UI.
  • Privacy controls, redaction boundary, deletion, no telemetry.
  • A reference agent skill explaining when to record a guess.
Phase 2

Similarity experiment

  • Select and package a lightweight local embedding model.
  • Lazy or post-insert generation; versioned vector storage.
  • Brute-force project-scoped cosine matching with CLI and browser suggestions.
  • Labeled evaluation set and threshold tuning.
Phase 3

Human-confirmed recurring subjects

  • Explicit grouping and ungrouping with stable subject ids.
  • Dismissed-match handling and cross-session recurring-guess summaries.
  • Experimental structural-locality adjustments using cwd and files.
Later, only if justified

Distribution and integrations

  • Automated releases, checksummed artifacts, Homebrew, winget, Scoop, go install.
  • Import, export, and backup ergonomics; project relocation and alias management.
  • Integrations with frick, editors, or agent protocols.
  • A richer UI, and a frontend toolchain only if vanilla JavaScript becomes a demonstrated constraint.

Resolved by the Phase 0 spike

Recommendations backed by measurements, recorded in docs/phase0-decisions.md. They answer Q1, Q2, Q4, and Q10 below.

Q1 ID formatULID via oklog/ulid/v2. 26 characters, time-sortable, no hyphens, and already the shape of the spec's examples.
Q2 CLI parserKong. Defaults render in help for free, enums validate at parse time, the command tree is one struct, small dependency footprint.
Q4 Input formOptions only. No example session needed stdin or JSON input. Deferred until an integration demonstrates a need.
Q10 SQLite drivermodernc.org/sqlite. Pure Go, cross-compiles without a C toolchain, per-process startup within 2 ms of the CGO driver. The wazero driver was rejected for ~420 ms startup per process. A fresh-database SQLITE_BUSY race was found by the multi-process stress script and fixed with an immediate transaction plus a bounded bootstrap retry.

Still open for engineering interrogation

To be resolved through focused research, prototypes, or measured use. The implementing agent brings back evidence and a recommendation rather than asking the owner to choose blindly.

  1. Which ID format best balances time ordering, Go support, and readability: UUIDv7 or ULID?
  2. Which Go CLI parser wins on maintenance, help UX, testability, and ergonomics, or is flag enough?
  3. What is the least surprising project identity and relocation workflow across Git worktrees, Jujutsu, monorepos, and no-VCS directories?
  4. Does v0.1 need stdin or structured JSON input, or is option-based recording enough?
  5. Which path fields display as absolute versus project-relative, and what conservative redaction defaults are appropriate?
  6. Are project config files useful enough to justify their precedence and privacy implications in v0.1?
  7. Which local embedding model and runtime give acceptable quality, size, cross-platform behavior, license, and Go integration?
  8. Should embeddings be generated after insert, lazily during review, or only by an explicit command?
  9. What labeled examples and success criteria are sufficient to enable similarity suggestions by default?
  10. Which Go SQLite driver best balances correctness, WAL behavior, single-binary builds, CGO, maintenance, and release complexity?

Guidance for coding-agent skills

Record a guess when you must choose among materially different outcomes and the specification, tests, documentation, or established project conventions do not clearly determine the answer.

Worth recording

  • Unspecified error, retry, fallback, or persistence behavior.
  • Destructive or data-retention semantics.
  • Security and authorization assumptions.
  • Compatibility and externally visible API decisions.
  • Inferred business rules and ambiguous acceptance criteria.
  • Deviations from a request.
  • Architecture choices where requirements do not distinguish the alternatives.

Usually not

  • Local variable names.
  • Formatting.
  • Mechanical refactors.
  • Obvious language idioms.
  • Choices fully determined by established project conventions.

An ideal guess says what was ambiguous, what was chosen, why, what alternative was plausible, and what the agent would have asked if asking were free. Record at the moment of the decision, not by reconstructing a ledger at the end of the run.

Final constraint

Blinken should earn complexity from observed use.

The first release needs to make one loop excellent: an agent encounters consequential ambiguity, records one cheap guess, a human sees the important guesses first, and the human accepts, rejects, or follows up. Everything else is optional until that loop proves useful.
